第二种 vs 第三种：数据流对比

把它理解成“内部闭环”与“内部闭环 + 外部证据增强”的区别。左边更像求职 CRM，右边更像带研究引擎的求职操作系统。

Option A

第二种：持续求职助手

主线是保存和复用候选人资产，让每次分析都站在上一次结果之上。

1. 用户输入 简历、手动粘贴 JD、投递状态、补充偏好
↓
2. 结构化层 `ResumeAsset -> CandidateProfile -> ResumeEvidence`
`raw_jd_text -> JobPosting -> JobRequirement`
↓
3. 工作流层 Supervisor / Workflow 决定进入匹配、改简历、面试准备或投递记录
↓
4. 输出层 MatchAssessment、ResumeVersion、InterviewPrepPack、ApplicationRecord
系统重点
  • 画像沉淀、版本管理、状态跟踪
  • 分析依据主要来自用户给的材料
  • 外部岗位认知弱时，结论保守但实现简单
Option B

第三种：研究增强型求职助手

保留左边全部流程，但在岗位侧自动补“真实 JD / 公司画像 / 面经 / 技术栈”证据。

1. 用户输入 简历、目标公司/岗位、可选 JD、投递状态、偏好
↓
2. 双通道采集 候选人通道：简历解析、画像沉淀
岗位通道：SearchAgent 检索真实 JD、公司线索、面经证据
↓
3. 证据融合层 `JobPosting + JobRequirement + ExternalEvidencePack`
对外部证据做时效、来源、置信度归因
↓
4. 工作流层 Supervisor 不只做匹配，还能输出“更像真实团队要求”的风险和准备动作
↓
5. 输出层 除基础产物外，再多 `Evidence-backed gaps`、公司差异卡、定向准备计划
系统重点
  • 内部资产和外部岗位信号一起驱动决策
  • 分析更贴近真实招聘场景，差异化更强
  • 要额外处理证据质量、去重、归因和时效性
对你当前仓库的直觉推荐： 如果目标是“最快落地”，先做第二种。 如果目标是“复用现有 Search / Query / Insight 能力，并做出明显差异化”，第三种更贴合这个项目的已有资产。
A

先做第二种

先把候选人资产、工作流、投递记录跑通，外部研究后补。

B

直接做第三种

从一开始就把现有研究引擎并进来，做更强的岗位侧增强。
