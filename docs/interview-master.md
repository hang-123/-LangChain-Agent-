# 面试总文档

日期：2026-05-12
用途：Java 开发 / Agent 开发 / RAG / Memory 面试统一题库

## 1. 项目总览

### 1.1 这个项目是做什么的

问题：

- 你先用 2 分钟介绍一下这个项目：解决什么问题、目标用户是谁、核心功能是什么？

标准答法：

“这个项目是一个面向求职和面试准备场景的多 Agent 研究系统。目标用户主要是需要做岗位分析、公司调研、简历定制和面试准备的求职者，尤其适合应届生和转岗用户。系统接收用户提供的公司、岗位、简历和求职目标后，自动完成意图识别、信息检索、风险诊断、行动项生成和报告输出，最终形成结构化的求职研究结果，而不只是简单返回一段对话文本。”

关键纠偏：

- 不要只说“信息收集”和“求职计划生成”，太窄。
- 要明确它还包含公司画像、岗位画像、匹配评估、风险诊断和报告校验。

### 1.2 为什么用 LangChain / LangGraph

问题：

- 为什么使用 LangChain / LangGraph？如果直接调模型 API，最大差异是什么？

标准答法：

“我选择 LangChain / LangGraph，不只是为了快速接模型，而是为了把多阶段任务拆成稳定、可回退、可观测的执行图。直接调 API 也能完成单轮问答，但如果要实现意图路由、检索、洞察生成、质量闸门、报告渲染这类多节点流程，就需要自己维护状态流转、工具调度、异常回退、消息协议和观测链路。框架帮我减少了底层编排成本，我可以把精力放在节点职责设计和质量控制上。”

关键纠偏：

- 不要只说“主流”“脚手架方便”。
- 要突出状态机编排、回退、观测、结构化上下文传递。

### 1.3 核心链路怎么讲

问题：

- 描述项目中最核心的一条请求链路。

标准答法：

`IntentRouter -> Search -> Query -> Insight -> QualityGate -> Report -> Review`

也可以展开成：

“用户输入岗位描述、目标公司、目标岗位和简历信息后，系统先做意图路由和输入规范化，然后进入 Search 阶段做岗位侧证据召回；接着 Query 阶段把证据收敛成带引用的结构化结论，Insight 阶段生成风险点和行动项；之后 QualityGate 做成稿前门禁，Report 负责结构化报告生成，Review 负责质量审查、回退和熔断，最后通过后再持久化并返回前端。”

关键纠偏：

- 不能只背节点名字。
- 必须知道每个节点的职责。

## 2. Agent 与架构

### 2.1 Agent / Tool / Service / Artifact 的边界

问题：

- 结合项目说明 `Agent`、`Tool`、`Service`、`Artifact` 四者边界。

标准答法：

- `Agent`：负责决策、推理、综合和生成
- `Tool`：负责调用外部能力或执行确定性能力
- `Service`：负责基础设施和确定性流程支撑
- `Artifact`：负责跨节点传递的结构化产物或共享契约

适合项目里的总结：

“Agent 负责判断和生成，Tool 负责拿能力，Service 负责托底和支撑，Artifact 负责把结果以结构化契约在节点之间传递。”

关键纠偏：

- `Artifact` 不是“人工”。
- 不要把普通节点和真正承担决策的 Agent 混在一起。

### 2.2 为什么不用开放式自主 Agent

问题：

- 为什么不做成开放式自主 Agent，而是固定状态机 + harness？

标准答法：

“我没有做开放式自主 Agent，是因为这个场景不是开放世界任务规划，而是围绕求职研究的固定深度流程。固定状态机的优势主要有四点：第一，稳定性更高，节点职责、回退边和熔断策略都可以显式定义；第二，可观测性更强，每个节点的输入、输出、耗时、失败原因和质量状态都可以追踪；第三，成本更可控，可以把复杂推理留给大模型，把检索、排序、规则校验等环节交给确定性模块；第四，调试和回归更容易，因为系统可以分节点定位问题，而不是把问题都包在一次大模型自主规划里。”

关键纠偏：

- 不要只说“黑箱”，要说可观测性、执行路径漂移、回归困难。
- 要强调这是固定深度流程，不是开放任务规划。

### 2.3 为什么不给模型自己选工具

问题：

- `SearchAgent` 为什么不让大模型自己决定调用哪些工具？

标准答法：

“我把工具调用权收敛到 Search 阶段的确定性调度里，牺牲的是灵活性，换来的是更强的稳定性、可解释性和更低的延迟。因为如果每次都让模型先读一遍工具 schema 再决定调用哪些工具，一方面 token 成本会升高，另一方面工具选择会受 prompt 和模型波动影响，导致相同输入的执行路径不稳定。对这个项目来说，工具集合和检索目标都比较明确，所以我更希望把工具选择做成 policy 和代码里的确定性逻辑，而不是依赖模型临场决定。”

关键纠偏：

- 记住两个关键词：`schema 注入成本`、`执行路径漂移`。

### 2.4 QualityGate 和 ReviewAgent 为什么拆开

问题：

- `QualityGate` 和 `ReviewAgent` 为什么拆成两个？

标准答法：

“我拆 `QualityGate` 和 `ReviewAgent`，不是单纯为了多审一层，而是为了把‘硬约束检查’和‘软质量判断 + 回退决策’分开。`QualityGate` 更像前置门禁，主要根据证据覆盖、结构完整性、质量阈值决定能不能进入正常输出或是否必须保守降级；`ReviewAgent` 则负责对最终结果做更细的审查，比如公司特异性是否足够、技术栈是否真正证据化、行动项是不是模板化，并根据 issue code 决定回退到 `Query / Insight / Report` 哪个节点。”

关键纠偏：

- 不是两次重复审查。
- 一个偏规则门禁，一个偏问题归因和回退。

### 2.5 renderer-first 的收益

问题：

- `renderer-first` 相比自由生成整份报告，收益是什么？

标准答法：

“`renderer-first` 的核心收益不只是格式统一，而是把报告主体变成由结构化数据驱动的渲染过程，减少整篇报告都靠大模型自由发挥。这样一来，section 顺序、字段来源、证据链接和关键结论都可以更多地来自上游 artifact，而不是依赖模型一次性编整篇长文。它同时解决了三个问题：结构一致性、事实边界控制和后续维护性。”

## 3. 质量控制与风险

### 3.1 如何避免模型胡编

问题：

- 如何保证最终生成内容不是模型胡编？

标准答法：

“我主要通过证据优先和双层校验来压制幻觉。前面 Search 节点先生成结构化证据，Query 节点要求结论绑定证据引用，Insight 节点在证据不足时不能强推结论，QualityGate 根据阈值决定是否进入保守模式，最后 Review 再从公司特异性、技术栈证据化、行动项证据绑定等维度做二次审查。也就是说，我不是靠一句 Prompt 让模型别胡编，而是靠整条链路让它没有太多胡编空间。”

### 3.2 检索工具超时或冲突怎么办

问题：

- 如果检索工具超时或返回冲突信息，链路怎么处理？

标准答法：

“如果某个检索 Tool 超时，Search 阶段不会直接让整轮任务失败，而是通过并发执行和单点失败容忍把异常收敛到 `retrieval_diagnostics / failure_breakdown`。如果返回信息冲突，系统不会强行拍板，而是保留冲突证据、标注不确定性，再由 Query / Insight 阶段控制结论力度，并由 QualityGate 和 Review 决定是保守降级、回退重写还是继续交付附带风险提示。”

### 3.3 最隐蔽的 Bug 是什么

问题：

- 系统里最容易出现“看起来对，其实是错”的隐蔽 Bug 是什么？如何监控或预防？

标准答法：

“我觉得最容易出现的隐蔽 Bug 是‘报告看起来很具体，但其实证据绑定是错的或者很弱’。比如公司画像写得很像定制化分析，但引用的是泛经验贴；或者技术栈结论看起来合理，但没有足够 JD、招聘页或高质量面经支撑。这类问题不会让系统报错，甚至用户第一眼也不一定看出来，所以风险很高。我的预防方式一是要求上游产出结构化 `evidence_items` 和 `evidence_refs`，二是用 `QualityGate` 检查 coverage 和阈值，三是让 `ReviewAgent` 检查公司特异性、技术栈证据化和行动项证据绑定，四是在 eval 里做分节点评分和 root cause 记录。”

## 4. RAG 基础

### 4.1 什么是 RAG

问题：

- 什么是 RAG？它解决的核心问题是什么？

标准答法：

“RAG 是 Retrieval-Augmented Generation，核心思想是在生成答案前先从外部知识源检索相关证据，再让模型基于这些证据生成，而不是只依赖参数记忆。它主要解决的是知识时效性、领域覆盖不足和事实性错误问题。”

关键纠偏：

- 不要把它概括成“解决提示词模糊”。

### 4.2 完整 RAG 流程

问题：

- 一个完整的 RAG 流程通常分成哪几个阶段？

标准答法：

1. 数据采集
2. 文档清洗与切块
3. 向量化与索引
4. 在线查询理解
5. 检索召回
6. 重排与筛选
7. 上下文构造
8. 基于证据生成
9. 可选后处理

### 4.3 向量检索为什么能工作

问题：

- 向量检索为什么能工作？

标准答法：

“向量检索之所以能工作，是因为 embedding 模型会把语义相近的文本映射到向量空间中相近的位置。用户 query 和文档 chunk 都会被编码成向量，然后通过余弦相似度、点积或欧氏距离来衡量相近程度，进而召回语义相关而不只是关键词完全重合的内容。”

关键纠偏：

- 不要把 `token` 和 `embedding` 混在一起。

### 4.4 RAG、数据库、全文检索、知识图谱的区别

问题：

- RAG 和传统数据库查询、全文检索、知识图谱的区别分别是什么？

标准答法：

- 传统数据库：结构化字段过滤和精确条件匹配
- 全文检索：基于倒排索引和 BM25 等相关性评分做关键词召回
- 向量检索 / RAG：偏语义召回
- 知识图谱：偏实体关系和多跳推理

关键纠偏：

- 全文检索不是 0/1 精确匹配。

### 4.5 chunk 为什么重要

问题：

- 文档切块为什么重要？chunk 太大或太小分别有什么问题？

标准答法：

“chunk 直接影响召回颗粒度和证据纯度。chunk 太大时，一个片段里会混入多个主题，embedding 容易被无关信息稀释，召回后还会浪费上下文窗口；chunk 太小时，虽然召回更细，但语义上下文不完整，容易把一句孤立的话拿出来，导致下游生成误读或证据不足。所以切块的目标不是越小越好，而是在语义完整性和召回精度之间找平衡。”

### 4.6 embedding 模型怎么选

问题：

- embedding 模型怎么选？要关注哪些指标？

标准答法：

“我选 embedding 模型不会只看榜单，而是会结合业务场景看语义召回效果、维度、延迟、成本和语言适配。比如如果是中文岗位资料检索，我会重点验证它在 JD、面经、技术栈描述上的召回质量；如果数据量大，我会关注维度对向量库存储和检索性能的影响；如果是高频在线检索，还要看单次 embedding 的延迟和吞吐。通常我会先用一个效果和成本平衡的模型做 baseline，再通过离线评测和真实 query 看 top-k 命中率、误召回和相关性表现，必要时再升级模型或补 rerank。”

### 4.7 为什么做混合检索

问题：

- 为什么很多 RAG 系统不只做向量检索，还要加 `BM25 / keyword search / metadata filter / rerank`？

标准答法：

“单纯向量检索擅长语义相似，但对精确关键词、专有名词、缩写、版本号、公司名、岗位名这类强字面信号不够稳定；而 BM25/关键词检索正好擅长命中这些字面特征。metadata filter 可以先把候选空间缩小到公司、岗位、时间范围，rerank 则负责在候选集合里做更细粒度的相关性排序。所以混合检索的本质，是把语义召回、字面召回和结构化约束结合起来，提高 recall 和 precision。”

### 4.8 为什么不能把召回内容全塞给模型

问题：

- 召回了 10 段文本，为什么不能全部塞给大模型？上下文构造时如何裁剪和组织？

标准答法：

“不能把 10 段文本全塞进去，因为召回结果里可能有重复、弱相关、过时或彼此冲突的信息，全部注入会增加 token 成本，还会稀释真正关键证据，导致模型抓不住重点。上下文构造时我通常会先去重，再按相关性、时效性、来源质量和任务目标筛选 top-k；然后保留必要的 metadata，比如来源、时间、标题；最后按主题或证据类型组织成结构化上下文，而不是简单拼接原文。”

### 4.9 RAG 常见错误模式

问题：

- 如果用户问“字节后端实习面试偏 Java 还是 Go”，RAG 最容易犯什么错？怎么降低错误率？

标准答法：

“这种题最容易出现的错误是把泛化信息当成岗位特异性结论。比如召回到几篇旧面经里提到 Go，就直接下结论说字节后端偏 Go；或者把通用后端岗经验贴误当成目标团队的真实要求。要降低错误率，首先要做 metadata filter，尽量限定公司、岗位、时间范围和来源类型；其次要做 source weighting，优先 JD、招聘页、近时间的高质量面经；再次要在生成阶段显式表达证据强弱，比如‘现有证据更偏向 Java，但团队差异较大，Go 也有出现’；最后可以做 claim-evidence binding，要求结论绑定具体证据来源。”

## 5. 项目里的 RAG 与 Memory

### 5.1 两者分别解决什么问题

问题：

- 在项目里，`RAG` 和 `memory` 分别解决什么问题？为什么两个都要有？

标准答法：

“RAG 和 memory 都在做检索，但检索对象不同。RAG 检索的是岗位和公司相关的外部证据，解决的是知识覆盖率、历史资料复用和外部事实支撑问题；memory 检索的是用户历史行为和偏好，解决的是个性化理解和跨轮次连续性问题。两个能力不能互相替代，因为只做 RAG，系统会懂岗位但不懂用户；只做 memory，系统会记住用户但缺少最新的外部岗位证据。”

### 5.2 RAG 在项目里的位置

问题：

- 在你的项目里，RAG 放在哪个节点，解决什么问题？

标准答法：

“RAG 放在 `SearchOrchestrator / SearchAgent` 这一层，作为实时 Web 检索之外的补充召回源。核心链路是：`Tavily 实时检索 + pgvector RAG 检索 -> 去重合并 -> 评分筛选 -> evidence_items`。它的作用不是替代实时搜索，而是增强检索覆盖率，尤其适合复用历史高质量岗位资料，比如历史 JD、历史面经、公司画像资料和技术栈资料。”

### 5.3 为什么把 RAG 放在 Search 层

问题：

- 为什么把 RAG 放在 `SearchOrchestrator / SearchAgent`，而不是放到 `AnalysisAgent` 或 `ReportAgent` 前面再检索一次？

标准答法：

“我把 RAG 放在 Search 阶段，而不是 Analysis 或 Report 前面补查，是因为 Search 是整个系统的统一证据入口。实时 Web 检索和 pgvector RAG 都属于岗位侧外部证据召回，把它们统一放在 Search 层处理，可以先完成去重、评分、时效性处理和 evidence_items 构建，再把一个更干净、更结构化的证据池交给下游分析和生成节点。这样下游节点只消费统一证据，而不用自己再做一次检索和证据清洗，边界会更清楚，链路也更稳定。”

关键词：

- `统一证据层`

### 5.4 memory 的三层结构

问题：

- 为什么 `Working Memory / STM / LTM` 不能合成一层？

标准答法：

“这三层不能合并，本质上是因为它们的生命周期、存储方式、访问频率和用途都不同。Working Memory 是一次执行内部的临时状态，STM 是短期会话级上下文，LTM 是跨 session 的长期沉淀。如果强行合并，会导致短期噪音污染长期记忆，也会让运行态上下文和持久化记忆边界混乱。”

### 5.5 RAG 和 memory 冲突怎么处理

问题：

- 如果 RAG 召回结果和 memory 里的用户历史偏好冲突，谁优先？系统怎么处理？

标准答法：

“如果 RAG 召回的岗位事实和 memory 里的用户历史偏好冲突，我不会简单说谁绝对优先，而是分角色处理。岗位事实类信息，比如岗位地点、技术要求、团队方向，应以当前检索证据为准；用户偏好类信息，比如城市偏好、岗位偏好，应保留为决策约束，但不能覆盖外部事实。最终系统应该把这种冲突显式表达出来，比如‘当前高质量岗位主要集中在北京，但用户历史偏好更偏上海’，然后由下游分析节点给出折中建议，而不是偷偷替用户做决定。”

### 5.6 这套架构最难做对的点

问题：

- 这套 `RAG + memory` 架构里最难做对的点是什么？

标准答法：

“我觉得最难做对的是检索结果如何进入后续推理而不污染上下文。RAG 的风险是召回结果太杂、太旧、太弱，导致模型基于低质量证据生成看似合理的结论；memory 的风险是历史偏好被过度强化，或者短期噪音被错误沉淀成长期记忆。所以难点不只是‘查到’，而是怎么做筛选、衰减、权重控制和边界隔离，让系统既能用到历史信息，又不被历史信息绑架。”

## 6. 项目里的 RAG 参数设计

### 6.1 当前 embedding 模型和原因

问题：

- 当前 embedding 模型选的是什么，为什么这么选？

标准答法：

“当前项目默认的 embedding 模型是 `text-embedding-3-small`，维度是 `1536`。这个项目里的 RAG 不是最核心的单点能力，而是挂在 Search 层上的一个补充召回源，所以选型更偏向‘够用、稳定、成本可控’，而不是一上来追求最强模型。`text-embedding-3-small` 的特点正好适合这种场景：成本相对低，延迟相对可控，1536 维表达能力够做 baseline，工程接入也比较简单。”

### 6.2 当前 chunk 策略

问题：

- 当前项目里 chunk 的策略是什么？

标准答法：

“当前实现先用了固定长度 chunk，默认 900 字符，没有做 overlap，也没有做复杂语义切块，主要是为了先把 RAG 检索能力稳定接进 Search 层。这个设计足够轻，但后续如果要继续优化，我会优先升级为按语义单元切块并保留 overlap。”

补充点：

- 默认 `chunk_size = 900`
- 按字符顺序切块
- 先做空白归一化
- 每个 chunk 继承 metadata

### 6.3 当前检索参数

问题：

- 当前项目里 RAG 还有哪些关键参数？

标准答法：

- `RAG_TOP_K = 4`
- `EMBEDDING_DIM = 1536`
- `OPENAI_EMBEDDING_MODEL = text-embedding-3-small`
- `ENABLE_RAG_WRITEBACK = false`
- `RAG_WRITEBACK_QUALITY_THRESHOLD = 70`

解释：

- top-k 取 4 是偏保守的小召回，目的是减少噪音
- 只允许 `jd`、`company_profile`、`interview`、`tech_stack`、`salary_culture` 进入 RAG 库
- RAG 只是补充源，不阻断主流程

### 6.4 时效性衰减怎么设计

问题：

- 当前项目里怎么防止旧资料污染 RAG 结果？

标准答法：

“项目里通过 `freshness_score` 和衰减倍率来控制旧资料影响。当前公式是 `freshness_score = max(0, 100 - days_since_ingestion * 2)`，也就是每天衰减 2 分；后面再按区间乘以不同倍率，低于 40 分的资料会被打上 `may_be_stale`。这套设计的意图很明确，就是防止旧资料看起来相关，但实际上误导当前结论。”

## 7. 高价值口径

### 7.1 项目里的 RAG + memory 复述版

“在我这个项目里，RAG 和 memory 是两套边界很清楚的能力。RAG 放在 SearchOrchestrator 这一层，主要做岗位侧外部证据召回，用 pgvector 检索历史 JD、面经和高质量岗位资料，再和实时 Web 检索结果去重合并，统一进入 evidence_items，解决的是检索覆盖率和历史资料复用问题。memory 则分成 Working Memory、STM 和 LTM 三层，分别处理当前 session 上下文、短期会话记录和跨 session 的长期偏好与模式沉淀。它的接入点是 memory_retrieval_node，会在执行开始时按 user_id 加载相关历史摘要和长期记忆，在执行结束后回写摘要并做长期记忆 consolidation。简单说，RAG 让系统更懂岗位，memory 让系统更懂用户，两者结合后，系统既能基于真实外部证据做分析，也能逐步形成对用户的个性化理解。”

### 7.2 项目里的 RAG 参数复述版

“当前项目里的 RAG 参数设计比较保守。比如 chunk 先采用固定长度切块，默认 900 字符，没有做 overlap，也没有上复杂的语义切块；embedding 模型默认是 `text-embedding-3-small`，维度 1536；每次 RAG 检索只取 top 4，避免把太多噪音带进上下文；只允许 JD、公司画像、面经、技术栈、薪资文化这 5 类岗位侧资料进入 RAG 库；同时对结果做 freshness score 和衰减倍率，控制旧资料对当前分析的污染。整体思路不是一上来把 RAG 做得很重，而是先把它作为 Search 层的补充召回源稳定接进去，再通过小 top-k、类型约束、时效衰减和质量阈值把风险收住。”

## 8. 最后提醒

- 不要把当前项目说成已经做了完整重型 RAG 系统
- 不要把全文检索说成 0/1 精确匹配
- 不要把 token 和 embedding 混在一起
- 不要把 RAG 放到意图识别节点
- 不要把岗位事实和用户偏好冲突简单说成“谁绝对优先”
